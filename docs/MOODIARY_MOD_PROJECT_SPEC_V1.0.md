# Moodiary 魔改项目长期开发规范 V1.0

> **状态：用户正式确认版**  
> **确认日期：2026-11-10**  
> **规范作用：长期维护、跨会话接替、代码审查和交付验收的唯一项目边界说明。**  
> 本文件不是新增功能的授权。修改规范、改变范围或增加功能，必须经用户明确批准；不能根据助手自己的推测扩大开发。

## 0. 基本原则与名词

- **官方原版**：GitHub [ZhuJHua/moodiary](https://github.com/ZhuJHua/moodiary) 作者发布的官方 Android App。用户已经在官方原版写了笔记。
- **魔改版**：我们基于官方 Moodiary 源码二次开发的 Android App。确认规范时魔改版尚无用户笔记。
- **最终魔改版**：未来长期写笔记的主力 App；不会与官方原版合并安装。
- **首次迁移**：官方原版已有笔记 → 最终魔改版。不是旧魔改 APK → 新魔改 APK 的历史记录迁移。
- **覆盖升级**：同一魔改 App 的旧正式版 → 新正式版，必须保留其既有本地数据和设置。
- 两个 App 各自独立；用户手机只长期安装官方原版与一个魔改版。
- 用户未来仅在魔改版主要写笔记；官方偶发新笔记由用户手动复制粘贴。**不开发两 App 自动增量合并或双向同步。**

## A. App 定义与使用方式（全部已确认）

| 编号 | 规范 |
|---|---|
| A01 | “原版”只指 ZhuJHua/moodiary 原作者发布的官方 App。 |
| A02 | “魔改版”指基于原版源码开发的独立 App。 |
| A03 | 手机长期只装两个 Moodiary：官方原版与魔改版。 |
| A04 | 已有笔记均在官方原版；确认规范时魔改版尚无用户笔记。 |
| A05 | 魔改版安全稳定后，未来笔记主要写入魔改版。 |
| A06 | 官方原版偶尔新增笔记，用户手动复制到魔改版。 |
| A07 | 官方原版主要作为官方功能与版本升级的参考。 |
| A08 | 官方新增相似功能不自动废弃魔改功能。 |

## B. 版本及上游升级机制（全部已确认）

| 编号 | 规范 |
|---|---|
| B01 | 魔改版对外显示版本号跟随**已适配的**官方原版版本号。 |
| B02 | 官方更新后，针对性分析与吸收有价值的功能、安全修复、性能与兼容修改。 |
| B03 | 上游升级必须尽可能保留全部现有魔改功能。 |
| B04 | 以原作者的**正式 Release / Tag** 为升级基准；不自动追踪未发布 main 分支。 |
| B05 | 只有完成对应 Release 的适配与测试，才将魔改版显示版本升级至该版本。 |
| B06 | 同一官方版本下使用独立内部 MOD Build 编号区分魔改构建；不强制界面显示该编号。 |
| B07 | 每次**正式交付的新魔改 APK**，Android 整数 `versionCode` 都必须比前次正式发布更大。 |
| B08 | 不因为上游可能更新就提前大规模重构稳定的魔改代码。 |
| B09 | 官方具备相似功能时，对比完整性、稳定性与兼容性，决定是否替换；默认保留魔改实现，不自动删除。 |

**维护方式：**记录 upstream Release Tag、精确 commit、魔改 patch/overlay 版本、MOD Build、`versionCode`、CI/真机验收结果。原作者升级后先做版本差异评估，再最小改动适配；禁止用新上游源码直接覆盖魔改文件。

## C. 数据迁移与长期数据保护（全部已确认）

| 编号 | 规范 |
|---|---|
| C01 | **一次性首次迁移：官方原版 App 笔记 → 最终魔改版 App**。 |
| C02 | 不开发原版与魔改版之间的自动增量迁移。 |
| C03 | 不开发两 App 双向自动同步与自动冲突合并。 |
| C04 | 不迁移不存在的旧魔改版 W9 历史数据；不能将此作为交付前置条件。 |
| C05 | 首选官方原版已有的备份导出能力；不能修改原版 App 或其数据。 |
| C06 | 首次迁移验收必须核对：应迁移日记数量、正文文字与富文本、创建时间与所属日期、分类、标签、地点及其他可用元数据、图片/音频/视频/附件的存在、内容与可用性（必要时比较 SHA-256）；失败必须明确报告，不得把部分成功标为全部成功。 |
| C07 | 迁移验证成功前，绝不卸载官方 App 或清除其数据。 |
| C08 | 此后魔改版采用同 App 覆盖升级，不再重复执行官方原版的全量迁移。 |
| C09 | 官方与魔改版独立包名及本地数据空间，不能互相覆盖。 |
| C10 | 官方与魔改版如使用坚果云 WebDAV，**必须使用不同远端目录**，防止写入同一同步空间。 |
| C11 | 对已有数据可能产生风险的升级，先确认存在**可恢复且经过核验的备份**；任何升级失败都不能自动清库、删除笔记或媒体。 |
| C12 | 涉及数据库 Schema/字段/迁移逻辑的改动，必须测试从既有正式数据版本升级到新版本；上游迁移与魔改迁移都要验证，确保原生日记、长期记录、日期映射、媒体关联和用户设置得到保留。 |

**区分两种过程：**官方 → 魔改的初次导入，和魔改正式版 → 下一魔改正式版的原地升级。后者不需要每次重新导入官方笔记。未来若用户主动决定再次导入官方笔记，必须另行讨论，不能悄然开发自动合并。

**既有 W9 完整历史备份代码：**不因用户不需要旧魔改数据迁移而随意删除已实现的功能；可以按已批准范围继续测试或修复真实安全问题，但不能把“旧魔改历史迁移”重新当成当前用户的数据前置条件。

## D. 安装、签名与交付（全部已确认）

| 编号 | 规范 |
|---|---|
| D01 | 魔改版与官方原版使用不同的 Android 应用包名，能同时安装。 |
| D02 | **魔改版首次正式发布前固定包名；以后正式版不得随意更改。** 具体字符串由正式发布方案确认，不能擅自假定早期测试包名已经最终获批。 |
| D03 | **首次正式发布前建立并安全保存一套独立、长期有效的签名密钥**，以后始终使用同一签名；私钥及密码不提交公开仓库。 |
| D04 | 魔改正式版必须能够直接覆盖旧魔改正式版，保留全部用户数据及设置；不要求卸载。 |
| D05 | 不要求手机长期安装第三个 Moodiary 测试版；测试优先在 CI、模拟器或隔离测试环境完成。 |
| D06 | 正式 APK 必须验收：与官方共存、包名及签名、版本规则、覆盖升级、官方保留功能、已批准魔改功能、笔记和长期记录完整性、媒体、备份恢复、数据库升级兼容性、稳定性、小米手机/实际系统环境的必要真机验证。**快速 CI 通过不等于正式交付**。 |

交付不要求绝对零 Bug；不得存在已知阻断正常使用、破坏用户数据或使已批准核心功能失效的严重问题。实际测试记录应区分通过、失败、跳过和未执行。

## E. 每轮开发的强制执行边界（用户明确提出）

1. **先分析需求，再动代码**：定位需要修改的具体文件、代码位置以及相关依赖。
2. **评估波及**：分析对数据、数据库、编辑器、原版功能、魔改功能、WebDAV、LAN、发布流程的实际影响。
3. **简述最小修改方案**，不擅自改变需求；遇关键不确定条件先向用户确认。
4. **只实现该轮已批准的功能/缺陷修复**；其他问题可以报告并列入待议，不得自行扩大范围。
5. 不随意重构无关代码，不删除已有功能，不改变不相关数据格式。
6. 修改完成必须运行针对性及必要回归测试；失败如实说明，不能靠禁用检查冒充通过。
7. 保留可复现的源码基线、上游 Tag/commit、补丁、测试记录。APK 降级不是数据库安全回滚方案；必须独立备份。
8. 每轮汇报：已改文件与理由、测试结果、未完成/阻断事项、正式交付状态。
9. 用户仅要求“讨论方案”“对齐规范”时禁止修改代码。
10. 对于官方新 Release：先比对差异，再隔离适配冲突，保持魔改功能和用户数据完整。

## 正式版本的交付闸门

1. 确认被支持的官方正式 Release 和原版备份格式；不得假定老式 Isar 备份与新版 ZIP 一定兼容。
2. 官方原版导出的备份由魔改版**只读解析来源**并导入到独立目标；核验 C06 的数据及媒体，原版保留不动。
3. 已批准的魔改功能、原版功能和数据迁移/恢复安全测试实际通过。
4. 按 B01/B05/B06/B07 实施版本管理，按 D01/D02/D03/D04 实施包名、签名及覆盖升级。
5. 按 D06 真机验收通过后才宣称可作为长期主力 App；未经通过的构建应标明“测试候选版”。

## 持久化及跨对话接替规则

- **此 Markdown 是规范 V1.0 的持久化来源**。新的会话、开发者或自动化工作开始 Moodiary 任务时，必须先阅读本文件，再查看当前开发分支及 CI；不得从聊天片段自行重新定义需求。
- **规范更新需要用户逐项明确确认**。任何代码迁移、结构重构、功能开发不能隐含更改本规范。
- README 应提供本规范入口；CI 应检查文件存在及关键边界，避免误删或错误回退。
- 本文档不包含密钥、私人日记或用户个人数据。

## 当前实现与规范之间待处理的差距（非新增需求授权）

- 早期构建脚本可能使用未发布的 upstream 提交、临时版本号及用于测试的包名；应在正式交付前按照 B04/B05/B07/D02 核对，而不是盲改大规模补丁链。
- 首次官方原版 ZIP 导入的自动化测试不等于已通过真实手机上的原版备份迁移；C06/D06 真机及实际原版版本验证仍必需。
- 数据库和媒体完整性需靠生产路径验收，不能只凭测试桩、源码编译或 CI 绿灯认定。
